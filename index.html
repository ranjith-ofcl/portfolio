stage 01

Read everything first, understand nothing yet

Every page gets plain-text OCR before any decision is made about it. This looks wasteful, since most pages in an annual report are narrative that will never be extracted, but it is the only way to classify a page on content rather than on position. Filings don't put the balance sheet on page 12 by agreement.

The output here is deliberately dumb: text and coordinates, no interpretation.

stage 02

Throw most of the document away

A page classifier sorts every page into one of six classes and routes only the financial statements onward. A 90-page filing typically contributes eight useful pages. Covers, auditor letters, directors' reports and narrative notes stop here.

This is the cheapest stage to get right and the most expensive to get wrong. Every page that survives costs money at every later stage, and every page wrongly dropped is silently missing data with no error to catch.

stage 03

Find the cells, not the words

Surviving pages go to table extraction, which returns cell boundaries and their contents. Financial tables break the assumptions general table parsers make: merged header cells spanning multiple periods, subtotal rows that look like data rows, footnote markers glued to numbers, and columns whose meaning is established several rows above where the numbers start.

stage 04

Work out what each column means

A grid of cells isn't data until you know which column is the current period, which is the prior, which holds line-item labels, and which is a note reference that must not be read as a value. Column headers are often absent, abbreviated, or sitting in a merged cell two rows up.

This stage assigns a role to every column, and everything downstream depends on it. A period column misread as a note reference produces a complete, plausible, wrong result.

stage 05

Rebuild the relationships the layout implied

Financial statements are trees rendered as flat tables. Indentation, ordering and subtotal placement encode parent/child structure that no cell contains explicitly. Property, plant and equipment belongs under non-current assets because of where it sits, not because anything says so.

This stage reconstructs that hierarchy as-is, without imposing an opinion about what the statement should look like.

stage 06

Only now does the client's schema enter

Stages one through five never learn who the client is. They resolve any filing, from any jurisdiction, in any format, into a faithful representation of itself. Only here does that neutral tree get mapped onto a particular client's required structure: their line-item taxonomy, their groupings, their naming.

This boundary is the most consequential design decision in the pipeline. Putting client specificity any earlier would mean a separate extraction path per client. Keeping it here makes onboarding a mapping exercise rather than an engineering project.

stage 07

Structured output, and a bill for it

The result is schema-conformant JSON with the source hierarchy intact. Every stage that touched it recorded its own token usage and cost, so the per-document figure is measured rather than estimated, and a regression in cost is as visible as a regression in accuracy.

architecture & cost

Nine services that don't know what order they run in

The pipeline's second version was eight workers in a fixed sequence inside one process. That worked until it needed to scale unevenly, fail partially, and be reasoned about per stage.

Discovery instead of ordering

The rewrite split it into nine independently containerized services. No service holds a reference to the next one; each finishes its work, writes state, and the next stage is resolved from the database. Pipeline order became data rather than code.

The practical payoff is that stages scale independently. OCR and table extraction are the expensive stages; classification is cheap. Under a fixed sequence they scaled together whether that made sense or not.

deployment alias drift

A deployment alias silently pointed at a different model than the configuration claimed. It surfaced because the pipeline reads the model name back out of every response's metadata instead of trusting what it asked for. Cost per document moved before anything about the output quality looked wrong, which is the argument for treating cost as a monitored signal rather than a monthly surprise.

Cost as a first-class metric

Every LLM call is attributed to the stage that made it, down to fractions of a cent, and aggregated per document and per batch. That instrumentation made the routing decision obvious: a small number of stages genuinely need a frontier model's reasoning, and the rest are classification and formatting work a much smaller model does just as well.

Routing by stage rather than using one model everywhere is what holds the per-document figure where it is.

number system handling

Filings group and punctuate numbers three different ways, and the pipeline resolves all of them: Western, European, and East Asian conventions. The same digits carry different values under each, so a figure parsed under the wrong convention is still a perfectly valid number in a perfectly valid schema, which means no validation rule will ever flag it. Detection has to happen per document.

Page classification

XLM-RoBERTa, fine-tuned for six-class page classification on multilingual filings. Trained both fully and with LoRA; the LoRA variant reaches 90.4% while training two tenths of one percent of the parameters, which makes retraining on new jurisdictions cheap enough to do routinely.

Per-class results were more useful than the aggregate. Balance sheet and cash flow pages classify perfectly. The weakest class is additional notes, whose boundary is genuinely blurry in the source documents rather than in the model.

why exact-match became the metric I trust

On financial tables, the pretrained structure model scored 81.2% token accuracy while producing no exactly correct table structures at all. Token accuracy averages over thousands of tokens per table, so one missing cell tag barely moves it and completely invalidates the table. Domain adaptation took validation accuracy from 34.6% to 81.6%, and exact-match is what showed the difference honestly.

Layout and table structure

PicoDet was fine-tuned for layout detection, reaching mAP 0.885 with table bounding-box IoU of 0.949 and detecting every table across a 295-table set. SLANeXt was fine-tuned for table structure recognition on annotated financial tables.

The Hybrid Result

The strongest configuration paired my fine-tuned cell-structure prediction with the commercial service's OCR text, matched spatially by intersection-over-union. I benchmarked it against Azure Document Intelligence across 100 real filings and 295 tables on row-count match, full structure match, numeric F1 and per-table latency.

Having those numbers is what made the platform decision straightforward rather than a matter of opinion, and the fine-tuned layout and classification models went into production regardless, where they do work the commercial service was never going to do for us.

inference_infrastructure

Somewhere to run open-weight models that isn't per-token

Once fine-tuned models existed, they needed serving. Paying per token for every call forever is a choice, and it's worth having an alternative to it.

What it does

A self-hosted vLLM gateway behind a FastAPI service, containerized, running on an A100 MIG slice. Models load on demand rather than at boot, so the gateway can offer a catalogue larger than the memory available to hold it.

Why on-demand mattered

The pipeline uses different models at different stages, and stage traffic is uneven. Keeping every model resident wastes most of the GPU most of the time, so loading on demand trades a cold start for the ability to serve more models than fit.

The failure mode worth designing for

The hard problem in a multi-model gateway isn't loading models, it's what happens when a load request arrives and the GPU is nearly full. A VRAM budget is enforced before any load begins, so the request is refused cleanly instead of failing halfway.

What that protects

Without the budget check, a load exhausts memory partway and takes down models that were serving traffic correctly, turning one bad request into an outage for unrelated stages. Idle models are evicted to reclaim space before it gets that far.

step 01

Why not just write scrapers

A hand-written scraper per registry is the obvious approach, and it's the right one until the registries change. Each site has its own layout, its own multi-step search, and its own habit of shifting selectors without notice. The maintenance cost scales with the number of jurisdictions and never stops.

step 02

The agent reads the page and decides

An LLM-driven browser agent handles that variability well. It reads the rendered page, works out which field wants the company name, fills it, and submits, recovering when a layout differs from what any fixed selector would have expected.

step 03

Picking the right result is the hard part

Registry search returns near-identical names: the same group's holding company, its local subsidiary, a dissolved entity with almost the same title. Choosing correctly needs the registration number and status read together, which is exactly the kind of judgement a selector can't encode.

step 04

Fetch the filing, not just the page

The agent opens the company record, identifies the annual return with financial statements among documents whose labels vary by jurisdiction, and downloads it. The file goes straight into the extraction pipeline as its input.

Along the way it handles JavaScript-rendered content, session and cookie state across multi-step flows, and anti-bot protection.

step 05

Memory replay: capture the route, not the result

This is the part I'd point at. Once the agent completes a lookup, it stores the exact navigation path it used, with the company-specific values swapped for placeholders. The route becomes a reusable artifact keyed to that registry.

Nothing about the page is remembered. What's remembered is the sequence of decisions that worked.

step 06

The second company costs nothing to find

Every later lookup on that registry matches the stored pattern and replays it directly, substituting the new company's details, with no model call at all. The agent becomes the fallback rather than the default: it runs on first contact with a registry, and again when a replay fails because the site genuinely changed, at which point it re-derives the route and overwrites the cached one.

The effect is to move the LLM off the hot path. Reasoning is used once, to discover something, and its result is captured as something cheap and repeatable. The expensive, variable component runs when the system meets novelty, not when it meets volume.
