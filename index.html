stage 01

Read everything first, understand nothing yet

Every page gets plain-text OCR before any decision is made about it. This looks wasteful, since most pages in an annual report are narrative that will never be extracted, but it's the only way to classify a page on content rather than on position. Filings don't put the balance sheet on page 12 by agreement.

The output at this stage is deliberately dumb: text and coordinates, no interpretation.

stage 02

Throw most of the document away

A page classifier sorts each page into one of six classes and routes only the financial statements onward. A 90-page filing typically contributes eight useful pages. Everything else stops here: covers, auditor letters, directors' reports, narrative notes.

This is the cheapest stage to get right and the most expensive to get wrong. Every page that survives costs money at every subsequent stage, and every page wrongly dropped is silently missing data with no error to catch.

stage 03

Find the cells, not the words

Surviving pages go to table extraction, which returns cell boundaries and their contents. Financial tables break the assumptions general table parsers make: merged header cells spanning multiple periods, subtotal rows that look like data rows, footnote markers glued to numbers, and columns whose meaning is established several rows above where the numbers start.

stage 04

Work out what each column means

A grid of cells isn't data until you know which column is the current period, which is the prior, which holds line-item labels, and which is a note reference that must not be read as a value. Column headers are often absent, abbreviated, or placed in a merged cell two rows up.

This stage assigns a role to every column. Everything downstream depends on it, which makes it the stage where a quiet error does the most damage. A period column misread as a note reference produces a complete, plausible, wrong result.

stage 05

Rebuild the relationships the layout implied

Financial statements are trees rendered as flat tables. Indentation, ordering, and subtotal placement encode parent/child structure that no cell contains explicitly. Property, plant and equipment belongs under non-current assets because of where it sits, not because anything says so.

This stage reconstructs that hierarchy as-is, without imposing an opinion about what the statement should look like. Getting this wrong doesn't produce garbage; it produces a tree that balances and means something different.

stage 06

Only now does the client's schema enter

Stages one through five never learn who the client is. They resolve any filing, from any jurisdiction, in any format, into a faithful representation of itself. Only at stage six does that neutral tree get mapped onto a particular client's required structure: their line-item taxonomy, their groupings, their naming.

This boundary is the single most consequential design decision in the pipeline. Putting client specificity anywhere earlier would mean a new extraction path per client. Keeping it here makes onboarding a mapping exercise rather than an engineering project.

stage 07

Structured output, and a bill for it

The result is schema-conformant JSON with the source hierarchy intact. Every stage that touched it recorded its own token usage and cost, so the per-document figure is measured rather than estimated, and a regression in cost is as visible as a regression in accuracy.

region · architecture & cost

Nine services that don't know what order they run in

The pipeline's second version was eight workers in a fixed sequence inside one process. That worked until it needed to scale unevenly, fail partially, and be reasoned about per stage.

Discovery instead of ordering

The rewrite split it into nine independently containerized services. No service holds a reference to the next one; each finishes its work, writes state, and the next stage is resolved from the database. Pipeline order became data rather than code.

The practical payoff is that stages scale independently. OCR and table extraction are the expensive stages; classification is cheap. Under a fixed sequence they scaled together whether that made sense or not.

Cost as a first-class metric

Every LLM call is attributed to the stage that made it, down to fractions of a cent, and aggregated per document and per batch. That instrumentation made the routing decision obvious: a small number of stages genuinely need a frontier model's reasoning, and the rest are classification and formatting work that a much smaller model does just as well.

Routing by stage rather than using one model everywhere is what holds the per-document figure where it is.

what the metadata caught

A deployment alias pointed at a different model than the configuration claimed. It surfaced because the pipeline reads the model name back out of each response's metadata rather than trusting what it asked for. Cost per document moved before anything about output quality looked wrong.

the decimal separator

European filings write thousands separators where other conventions write decimal points. Parsed with the wrong assumption, a value silently becomes a thousandth of itself: a perfectly valid number, in a perfectly valid schema, that no validation rule flags.

region · model_training

Four fine-tunes, and a recommendation not to ship them

Commercial document AI services are good at general documents. Financial statements are not general documents. That gap is worth measuring rather than assuming, in either direction.

Page classification

XLM-RoBERTa, fine-tuned for six-class page classification on multilingual filings. Trained both fully and with LoRA; the LoRA variant trains a fraction of a percent of the parameters and gets there.

Per-class results were more useful than the aggregate. Balance sheet and cash flow pages classified perfectly; the weakest class was additional notes, which is the class whose boundary is genuinely blurry in the source documents rather than in the model.

the finding that changed how I read metrics

Before fine-tuning, the pretrained structure model scored 81.2% token accuracy on financial tables and produced zero exact structure matches across fifteen tables. Not a low number. None.

Token accuracy averages over thousands of tokens per table. A single missing cell tag barely moves it and completely invalidates the table. The aggregate metric was reporting near-success on a model that was unusable for the task, and only exact-match told the truth.

The hybrid, and the honest result

The best-performing configuration paired my fine-tuned cell-structure prediction with the commercial service's OCR text, matched spatially by IoU. It was benchmarked against Azure Document Intelligence across 100 real filings and 295 tables on row-count match, full structure match, numeric F1, and per-table latency.

It did not win. Full structure match was 16.3%, numeric F1 76.9%. A third option scored higher on numeric F1 than either, at roughly ten times the latency per table.

So the recommendation was to stay on the commercial service. Fine-tuning had proved necessary, since the pretrained models were not merely worse but unusable, and it still hadn't proved sufficient. Those are different conclusions, and the useful outcome of the work was knowing which one applied.

region · inference_infrastructure

Somewhere to run open-weight models that isn't per-token

Once fine-tuned models existed, they needed serving. Paying per token for every call forever is a choice, and it's worth having an alternative to it.

What it does

A self-hosted vLLM gateway behind a FastAPI service, containerized, running on an A100 MIG slice. Models load on demand rather than at boot, so the gateway can offer more models than fit in memory at once.

A VRAM budget is enforced before any load is attempted, so a request for a model that won't fit is refused cleanly instead of failing partway through and taking the resident models down with it. Idle models are evicted to reclaim the space.

Why on-demand mattered

The pipeline uses different models at different stages, and stage traffic is uneven. Keeping every model resident wastes most of the GPU most of the time. Loading on demand trades a cold-start delay for the ability to serve a catalogue larger than the hardware.

the failure mode worth designing for

The interesting problem in a multi-model gateway isn't loading models. It's what happens when a load request arrives and the GPU is nearly full.

Without a budget check, the load starts, exhausts memory partway, and takes down models that were serving traffic correctly. One bad request becomes an outage for unrelated stages. Checking first turns that into a refused request.

Stack

vLLM, FastAPI, Docker, Hugging Face Transformers, 4-bit quantization via BitsAndBytes, NVIDIA A100 with MIG partitioning.

region · web_navigation_agent

An agent that stops being an agent once it knows the way

Company filings live in government registries, one per jurisdiction, each with its own search flow, session handling, and idea of how a form should work. The documents feeding the extraction pipeline have to be fetched before they can be read.

Why not just write scrapers

A hand-written scraper per registry is the obvious approach, and it's the right one until the registries change. Each site has its own layout, its own multi-step search, and its own habit of shifting selectors without notice. The maintenance cost scales with the number of jurisdictions and never stops.

An LLM-driven browser agent handles that variability well. It reads the page, decides where to click, and recovers when a layout differs from what a fixed selector expected.

Why not just use the agent

Because it's slow and it costs money on every run, and the second company you look up on a given registry follows exactly the same path as the first. Paying a model to rediscover a known route is waste, and it introduces variance into a process that was deterministic the moment the route was known.

Memory replay

So the agent records its successful navigation path, with the company-specific values replaced by placeholders. The next lookup on the same registry matches that stored pattern and replays the sequence directly, substituting the new company's details, with no model call at all.

The agent is the fallback rather than the default. It runs on the first encounter with a registry, and again when a replay fails because the site genuinely changed, at which point it re-derives the path and overwrites the cached one.

what this pattern is really doing

It moves the LLM from the hot path to the cold path. Reasoning is used once, to discover something, and its result is captured as something cheap and repeatable. The expensive, variable component runs when the system encounters novelty, not when it encounters volume.

Also handled

JavaScript-rendered content, session and cookie state across multi-step flows, anti-bot protection, and document download with face-page extraction. Built with Playwright, Selenium, and BeautifulSoup depending on what a given target needed. Led two developers on delivery.
